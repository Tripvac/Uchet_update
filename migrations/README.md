# Миграции БД

Схема БД описана нумерованными SQL-файлами. **ORM и Alembic не используются**
(по ТЗ проект остаётся на голом psycopg2). Единственный источник правды о
схеме — эти файлы; применяются строго по порядку номера.

## Порядок применения

| Файл | Что создаёт |
| --- | --- |
| `000_base_tables.sql` | Базовые таблицы: `bot_sessions`, `telegram_users`, `faq_items`, `faq_translations` |
| `001_init_content.sql` | Редактируемый контент: `bot_links`, `bot_content`, `bot_media` + начальные данные |
| `002_add_events.sql` | Статистика: `bot_events` + индекс `(ts, screen_id)` |
| `003_report_views.sql` | SQL-view для отчётов по `bot_events` |

Новую миграцию добавляем следующим номером: `004_*.sql`, `005_*.sql`, ...

## Как применить

### Вариант 1 — раннер (рекомендуется, поднимает схему одной командой)

Из корня репозитория, с заполненным `.env`:

```bash
python migrations/apply_migrations.py
```

Раннер:
- создаёт служебную таблицу `schema_migrations` (учёт применённого);
- применяет только ещё не применённые файлы, каждый в своей транзакции;
- повторный запуск безопасен — уже применённые файлы пропускаются.

`python init_db.py` делает ровно то же самое (обёртка над раннером).

### Вариант 2 — вручную через SQL Editor (Neon)

Открыть каждый файл по порядку и выполнить его содержимое в SQL Editor.
Так контент правит и администратор (см. `admin.md`).

## Идемпотентность

Все файлы написаны через `CREATE TABLE IF NOT EXISTS`,
`INSERT ... ON CONFLICT DO UPDATE` и `CREATE OR REPLACE VIEW`, поэтому их
безопасно применять и на уже существующей базе (текущая Neon, где таблицы
были созданы руками): первый прогон раннера просто отметит их как
применённые, ничего не сломав.
